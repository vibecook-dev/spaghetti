## 1. Questions

This phase answers two bounded questions before production refactoring:

1. Can the native Claude, Codex, and Grok surfaces produce a complete,
   display-capable project/session catalog without full transcript ingestion?
2. Can the high-volume permanent diagnostic ledger be represented as exact
   aggregates rather than one durable row per occurrence?

It does not answer final Rust startup latency, UI paint latency, query latency
during background ingest, selected-session hydration, FTS strategy, or final
background convergence. Those require the implementation phases in the RFC
012 plan.

## 2. Experiment design

### 2.1 Independence

The catalog census reads native roots directly and does not call Spaghetti
adapters or reuse their Rust decoders. It models only the bounded native
evidence needed for the hypothesis:

- Claude project directories, session indexes, top-level transcript
  membership, nested subagent parent-session membership, and bounded parent
  transcript heads;
- Codex bounded rollout heads beginning with `session_meta`; and
- Grok session-directory membership, summaries, and bounded chat fallback.

The comparison oracle is an existing Spaghetti database opened with SQLite
`mode=ro` and `PRAGMA query_only=ON`. Project identity is the union of canonical
session, session-index, and project-memory evidence. Session catalog identity
is the union of canonical transcript-backed sessions and native session-index
entries.

This is deliberately not a production parser. Validated mechanics must move
into common Rust source drivers; agent interpretation remains in adapters.

### 2.2 Privacy

Native paths, project/session IDs, prompts, titles, and payloads are held only
in process memory. JSON reports contain aggregate counts, field coverage,
bytes, timings, and SHA-256 identity digests. Mismatch samples are hashed.

The diagnostic census does not emit error messages or native payloads. It
emits aggregate counts and hashed diagnostic signatures.

### 2.3 Bounds

The selected run uses:

- 64 KiB maximum bytes from a transcript/rollout head;
- 1 MiB maximum for a native metadata document;
- no transcript-tail reads;
- no full JSONL record census; and
- no writes to native roots or the oracle database.

The feasibility script discards an incomplete logical JSONL record at the byte
boundary. This behavior is useful for finding a safe record bound, but the
production Rust driver must read one complete logical record up to its declared
maximum and report an explicit over-limit state.

## 3. Environment and inputs

- Apple M1 Max reference host, arm64
- macOS 26.5.2
- Python 3.14.0
- live native roots: approximately 3.6 GB Claude, 3.0 GB Codex, and 1.4 GB Grok
- oracle database:
  `~/Library/Application Support/@vibecook/spaghetti-playground/Cache/spaghetti-rs.db`
- oracle size at the selected run: 8,253,247,488 bytes
- oracle is the retained playground database corresponding to the same
  176-project/1,233-transcript-session production-shaped profile family

The live roots were not frozen and the operating-system filesystem cache was
not flushed. Therefore identity/byte counts are stronger evidence than the
sub-second Python wall timings. The selected run detected one Codex session
whose native creation time was 1 hour 3 minutes after the oracle database
mtime; it is reported as live drift, not a census false positive.

## 4. Reproduction

Focused tests:

```sh
python3 scripts/catalog_census/test_census.py
```

Checked-in fixtures:

```sh
python3 scripts/catalog_census/census.py \
  --claude-root crates/spaghetti-napi/fixtures/small/.claude \
  --codex-root crates/spaghetti-napi/fixtures/small-codex/.codex \
  --grok-root crates/spaghetti-napi/fixtures/small-grok/.grok \
  --out /private/tmp/spaghetti-catalog-census-fixtures.json
```

Live 64 KiB census and oracle comparison:

```sh
python3 scripts/catalog_census/census.py \
  --oracle-db "$HOME/Library/Application Support/@vibecook/spaghetti-playground/Cache/spaghetti-rs.db" \
  --head-bytes 65536 \
  --out /private/tmp/spaghetti-catalog-census-live-64k.json
```

Budget sweep replaces `65536` with `4096`, `16384`, `32768`, `49152`, and
`262144` and uses a distinct output path.

Diagnostic aggregation census:

```sh
python3 scripts/diagnostic_census/census.py \
  --database "$HOME/Library/Application Support/@vibecook/spaghetti-playground/Cache/spaghetti-rs.db" \
  --out /private/tmp/spaghetti-diagnostic-census-live.json
```

Equivalent package commands are `pnpm experiment:catalog-census`,
`pnpm experiment:diagnostic-census --database <path>`, and
`pnpm test:catalog-census`.

Claude and Grok project/session identity sets match the oracle exactly. Codex

### 6.2 Metadata coverage

| Agent  | Project display path | Session cwd | Native display label | Created time | Modified time | Native message count |
| ------ | -------------------: | ----------: | -------------------: | -----------: | ------------: | -------------------: |
| Claude |                91/99 | 1,079/1,113 |            535/1,113 |    612/1,113 |     624/1,113 |            242/1,113 |
| Codex  |                48/48 |     177/177 |              136/177 |      177/177 |       177/177 |                0/177 |
| Grok   |                29/29 |     125/125 |               84/125 |      125/125 |       125/125 |              125/125 |

Where both bounded census and oracle supplied values:

- Claude cwd matched in 1,028 of 1,067 comparable sessions (96.3%);
- Claude first prompt matched in 515 of 535 comparable sessions (96.3%);
- Claude title/summary matched in 358 of 359 comparable sessions (99.7%);
- Claude native message count matched all 242 comparable sessions;
- Codex cwd, created time, and bounded first prompt matched every comparable
  oracle session after applying the modeled 200 UTF-16-unit normalization; and
- Grok cwd, created time, and title/summary matched every comparable session.

Created-time mismatch for many Claude index records is expected because the
experiment retains native scalar forms while the canonical projection applies
timestamp qualification/normalization. The production catalog fact must use
the adapter's qualified timestamp semantics, not the experiment's raw scalar.

Native display labels are not complete, especially for Claude nested-only
parent sessions and Grok histories without generated titles. Identity and
project visibility remain complete. The UI therefore needs a deterministic
fallback; increasing transcript reads is not required for catalog correctness.

### 6.3 Catalog versus transcript truth

The oracle contains 1,233 transcript-backed canonical sessions:

| Agent  | Transcript-backed sessions |
| ------ | -------------------------: |
| Claude |                        932 |
| Codex  |                        176 |
| Grok   |                        125 |

Claude's native session indexes add 181 identities not backed by a currently
canonical transcript, producing 1,113 Claude catalog sessions and 1,414 total
oracle catalog sessions.

This result rejects using `canonical_sessions` alone as the phase-one library
catalog and also rejects turning session-index entries into fabricated complete
sessions. RFC 012 requires catalog membership plus explicit content
availability.

### 6.4 Claude membership detail

A top-level-only Claude scan found 382 parent transcript files and would have
missed the final history identity set. Nested `projects/<project>/<session>/`
directories containing subagent transcripts proved 729 parent-session
identities. Their union contained exactly the 932 transcript-backed Claude
sessions, including 550 nested-only sessions. Session-index evidence then
added the metadata-only identities.

The production Claude catalog declaration must therefore compose all three
evidence sources. This is a concrete example of why agents select common
components rather than being forced through one transcript-file abstraction.

## 7. Head-budget sweep

The table reports the live census at each arbitrary byte-prefix limit. Timings
were warm and are included only as directional evidence.

| Head bound | Total bytes read | Summed adapter time | Codex identities found | Codex labels found | Complete Codex identity set?                                            |
| ---------: | ---------------: | ------------------: | ---------------------: | -----------------: | ----------------------------------------------------------------------- |
|      4 KiB |        3,128,668 |            199.2 ms |                      6 |                  0 | No                                                                      |
|     16 KiB |       11,229,583 |            161.1 ms |                     37 |                  9 | No                                                                      |
|     32 KiB |       21,759,374 |            201.5 ms |                    176 |                 26 | No; four headers exceeded the boundary and live-set identities differed |
|     48 KiB |       31,241,287 |            241.4 ms |                    177 |                 83 | Yes on this live set                                                    |
|     64 KiB |       39,982,184 |            270.6 ms |                    177 |                136 | Yes; selected safety bound                                              |
|    256 KiB |      137,007,790 |            896.0 ms |                    177 |                145 | Yes                                                                     |

Codex `session_meta` can be a large first logical JSONL record because it
contains native instruction/configuration fields. A fixed 4–16 KiB byte prefix
cannot even identify most sessions. A production `DelimitedFirstRecord`
component must instead read one complete record with a declared maximum.

The 256 KiB head reads approximately 97 MB more than 64 KiB for nine additional
Codex labels. This is not a good phase-one trade-off. The selected design uses
64 KiB for identity and bounded label discovery, then relies on honest fallback
labels and background hydration.

## 8. Diagnostic aggregation result

The retained playground database had a slightly newer diagnostic state than
the original cold profile: 457,239 permanent occurrences rather than 457,311.
The census found:

| Metric                                          |       Result |
| ----------------------------------------------- | -----------: |
| Permanent diagnostic occurrences                |      457,239 |
| Distinct diagnostic signatures                  |           28 |
| Object-generation-signature groups              |        1,444 |
| Distinct payload hashes                         |      222,733 |
| Raw payload bytes in error rows                 |            0 |
| Object-generation row reduction opportunity     |     99.6842% |
| Global-signature-only row reduction opportunity |     99.9939% |
| Error table allocation                          | 89,907,200 B |
| Error primary-key index allocation              | 20,353,024 B |
| Unknown fact rows                               |      457,211 |

Per adapter:

| Agent  | Occurrences | Signatures | Object-generation groups |
| ------ | ----------: | ---------: | -----------------------: |
| Grok   |     398,745 |         12 |                      932 |
| Codex  |      58,488 |         15 |                      507 |
| Claude |           6 |          1 |                        5 |

The largest recognized shapes were Grok `phase_changed` (360,754
occurrences), Codex `item_completed` (44,435), Grok tool and permission
lifecycle families (approximately 9,265 each), and Codex `patch_apply_end`
(8,639). Their native meaning still needs ADS evidence and an explicit
disposition; volume alone does not authorize suppression.

All 457,211 `unknown_record` fact payloads use the existing `omitted` codec, so
the durable multiplication is mostly provenance/row/index overhead rather than
retained raw bodies. A correct aggregate can retain exact count and first/last
provenance while keeping bounded payload hashes/examples. It cannot retain
only 28 global rows because object/generation reconciliation and drift locality
would be lost.

## 9. Conclusions

### 9.1 Accepted conclusions

1. Complete multi-agent catalog identity is feasible with bounded I/O far
   below full transcript volume.
2. The application can use catalog readiness as an interactive boundary
   without creating a second source of truth.
3. Catalog facts must be separate from transcript-backed session facts.
4. Claude requires composed index, parent-transcript, and nested-membership
   evidence.
5. Codex requires a complete bounded first-record primitive; arbitrary tiny
   prefixes are incorrect.
6. Grok can use membership plus summary documents without chat/event ingest.
7. Missing native labels are normal and require qualified fields plus UI
   fallbacks.
8. A 64 KiB head is the selected initial bound for the measured Codex surface;
   it belongs in a versioned ADS/decoder contract.
9. Diagnostics have a strong aggregation opportunity at object-generation
   granularity.
10. Known-versus-unknown disposition work is part of adapter adaptation, not a
    storage-only optimization.

### 9.2 Not yet accepted

- the Python wall time as the Rust/product cold-start latency;
- a 2-second production SLO without a Rust cold-cache run;
- exposing background-built history before integrity gates;
- any FTS finalization strategy;
- diagnostic row reduction without production transaction/convergence tests;
- suppressing any native record family based only on frequency;
- partial transcript rendering; or
- the physical crate split.

## 10. Next evidence gates

1. Reproduce the identity digests with common Rust source drivers and catalog
   facts.
2. Freeze a three-source corpus so source mutation cannot create oracle drift.
3. Measure true cold and warm catalog phases in the production host.
4. Add catalog projection/query and background query-latency measurements.
5. Inject crashes and source mutations at every phase boundary.
6. Classify high-volume diagnostic families from pinned native evidence, then
   rerun whole-database T-C-T.
7. Compare safe foreign-key and FTS policies after catalog readiness.

Until those gates pass, the experiments justify the RFC and implementation
work but do not change production readiness behavior.
